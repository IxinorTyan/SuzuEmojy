# Nuitka 打包速度与缓存

照常运行 `python build_nuitka.py` 或 `build_nuitka.bat`。

- 默认按 CPU 和物理内存限制 C 编译并发：给系统预留 4 GiB，每个编译进程预算 2 GiB。这是避免高并发导致换页的保守估算，不是内存硬限制，也不保证所有机器都更快。这台约 16 GB、16 线程的机器默认使用 5 个进程。
- 可以用 `python build_nuitka.py --jobs 8` 手动调整。比较日志中的 `Nuitka compilation` 耗时，选择适合自己机器的并发数。
- 更新器使用稳定的 `dist/updater-dist` 输出和 `dist/updater-build` 工作目录。每次仍运行 PyInstaller 的依赖检查；发布目录重建不会再强制重建相同的更新器。
- 更新器入口、更新协议、打包脚本、Python 或 PyInstaller 版本变化会强制重新构建。输入文件用内容哈希检查，恢复旧时间戳也能识别这几个关键文件的变化。其它依赖由 PyInstaller 检查。
- 不再主动删除 `dist/main.build` 和另一种打包方式的根 `build` 目录。不过当前 Nuitka 4.0.5 自身会重新生成 C 和对象文件；不能把保留这个目录等同于跳过未修改模块的编译。Zig/Nuitka 的全局编译缓存仍按工具自身规则复用，请保留其缓存目录以及稳定的源码目录。
- 不改变优化等级、LTO 默认策略、AVX2 架构设置、依赖排除规则或发布内容；ZIP 仍采用原有的 DEFLATE 6 级压缩。增加的缓存只占开发机器空间，不进入发布包。
- 日志分别输出 Nuitka 编译、更新器、清单校验、ZIP 和总耗时，便于定位剩余瓶颈。首次编译没有热缓存，仍可能很慢。

`python build_nuitka.py --dry-run` 只查看计划，不编译或清理文件。

`python build_nuitka.py --clean` 重建项目中间目录并强制重建更新器，不清空 Nuitka/Zig 全局缓存。通常在排查构建异常时使用，无须每次执行。

回归检查：`python -B -m unittest discover -s tests -p test_build_packaging.py -q`。完整主程序的提速比例和实际发布包大小，需要在同一源码、依赖与机器上对照完整构建确认，不能用更新器的测量代替。

2026-10-18 本机隔离实测：同一份更新器源码，原命令约 13.1 秒，新流程首次约 14.6 秒、缓存构建约 3.5 秒。新流程首次与缓存构建的 EXE 大小和 SHA-256 完全一致；原命令生成 8,991,149 字节，新流程生成 8,991,043 字节，没有增大。不同次完整构建本身可能有少量字节波动。测试没有覆盖整个 Nuitka 发布包。
